# 1. 커뮤니티 캔버스

## 기획 의도

커뮤니티 캔버스는 네모닉의 출력된 메모 특성을 가장 직관적으로 보여주는 핵심 대표 콘텐츠이자 사이트 내
단일 공용 벽이다. 사용자는 새 메모를 작성하거나 릴레이 드로잉, 오늘의 운세, 플립북, 무한 캔버스 등
다른 부스에서 만든 결과물을 메모지로 출력해 벽에 자유롭게 부착한다.

방문자는 이 벽에서 타인의 자랑거리를 방명록처럼 감상한다. 결과물이 곧 공간이 되므로 별도 갤러리 없이
벽 자체가 전시 공간 역할을 한다.

## 핵심 재미 요소

- 내가 쓴 메모가 3D 공간에 남는 경험
- 메모를 어디에 붙일지 선택하는 인터랙션
- 벽이 점점 채워지며 살아 있는 느낌
- 다른 사용자의 메모를 건드리면 팔락이는 물리적 반응

## 1차 개발 범위

프론트엔드 디자인과 연동을 먼저 안정화하기 위해 1차 범위는 커뮤니티 메모의 기본 CRUD와 50개 FIFO 정책에
집중한다.

포함 범위:

- 공용 벽 메모 목록 조회
- 메모 상세 조회
- 직접 작성 또는 갤러리 결과물을 바탕으로 만든 최종 게시 이미지 생성 및 부착
- 커뮤니티 게시용 원본 이미지와 썸네일 이미지 저장 및 응답
- 게시 전 OCR/텍스트 모더레이션을 통한 부적절 콘텐츠 차단
- 본인 메모의 위치, 회전, z-index 수정
- 본인 메모의 편집 상태 JSON 저장 및 반환
- 본인 메모 삭제
- 새 메모 생성 시점의 50개 FIFO 자동 정리

후속 범위:

- 신고 기능
- AI 모더레이션 모델 고도화와 운영 임계값 튜닝
- 백오피스 숨김 메모 검토, 복원, 삭제
- 실시간 벽 동기화
- 커뮤니티 메모 외부 공유
- 게시 후 시각적 내용 재수정과 최종 이미지 교체

기본 CRUD/FIFO 단계에서는 WebSocket을 사용하지 않는다. 메모 생성, 수정, 삭제 후 프론트가 목록을 다시
조회하는 방식으로 화면을 갱신한다. 다른 사용자가 붙인 메모가 즉시 반영되는 라이브 벽 경험이 필요해지는
시점에 WebSocket 또는 SSE를 후속으로 검토한다.

## 메모 생명주기

- 캔버스 벽은 최대 50개의 메모를 유지한다.
- 새 메모가 부착되어 한도를 초과하면 가장 오래 부착된 메모부터 순차 제거한다.
- 제거 정책은 FIFO이다.
- 메모는 시간 제한 없이 벽에 남아 있으며, 갯수 기반 정책만 적용한다.
- 제거 임박 메모, 예를 들어 가장 오래된 5개에는 색 바램, 투명도 변화 등 퇴장 연출을 적용할 수 있다.
- FIFO로 제거된 메모는 DB에서 하드 삭제하지 않는다.
- FIFO 제거 시 `deleted_at`을 기록하고 `deleted_reason = expired`로 소프트 삭제한다.
- FIFO 갯수 검증은 메모 CREATE, 즉 부착 시점에만 실행한다.
- 사용자 삭제, 운영자 숨김 해제, 운영자 복원 등 다른 경로에서는 별도 갯수 검증을 하지 않는다.
- 복원 등으로 일시적으로 51개 이상이 되어도 다음 CREATE 시점에 FIFO가 자연스럽게 정리한다.
- 부적절 콘텐츠의 최초 노출 리스크는 게시 전 AI 모더레이션 차단으로 줄이고, 게시 후 리스크는 신고 5회 자동 숨김으로 보완한다.
- 숨김 상태 메모는 벽 렌더링에서 제외되며 갯수 한도 50개 카운트에도 포함하지 않는다.

## 사용자 인증 및 소유권

서비스는 회원가입과 로그인 없이 운영한다. 사용자 식별은 클라이언트 측 익명 UUID 기반이다.

| 항목 | 정책 |
| --- | --- |
| 식별자 생성 | 최초 방문 시 고유 UUID 생성 |
| 주 저장소 | `localStorage`에 UUID 저장 |
| 보조 저장소 | `cookie`에 동일 UUID 백업 저장 |
| 서버 연동 | 기존 익명 사용자 UUID를 `Anonymous-User-UUID` 요청 헤더로 전달 |
| 소유권 확인 | 데코레이션 수정, 배치 수정, 삭제 요청 시 헤더 UUID와 작성자 UUID 대조 |

### 소유권 정책

- UUID가 유효한 동안에만 본인 메모의 배치 수정과 삭제가 가능하다.
- 커뮤니티 벽과 후속 공유에서 실제로 노출되는 기준은 게시 시점에 생성된 최종 이미지 스냅샷이다.
- 게시 후 시각적 내용을 바꾸는 기능은 후속 범위이며, 이때는 프론트가 편집 상태를 다시 렌더링해 새 최종 원본 이미지와 썸네일 이미지를 업로드해야 한다.
- 1차 범위에서는 `decoration` JSON을 생성/조회 응답에 포함하지만, 별도 수정 API로 갱신하지 않는다.
- 갤러리에서 불러온 원본 결과물과 연결된 `artifact`는 수정할 수 없다.
- 벽 위 배치 정보인 `position_x`, `position_y`, `z_index`, `rotation_deg`는 본인 메모에 한해 수정할 수 있다.
- 편집 상태 데이터는 프론트가 정의한 JSON 덩어리로 저장하며, 백엔드는 내부 구조를 해석하지 않고 그대로 저장하고 반환한다.
- 시간 제한은 없으며, FIFO로 제거되기 전까지 본인 메모의 편집 상태와 배치 정보 수정이 가능하다.
- 브라우저 캐시 또는 데이터를 삭제하면 소유권을 잃는다.
- 소유권을 잃은 메모는 데코레이션 수정이 불가능하다.
- 고아 메모도 FIFO 한도 정책으로 제거되므로 영구 잔존하지 않는다.

### 모바일 환경

| 환경 | 동작 | 비고 |
| --- | --- | --- |
| 모바일 일반 브라우저 | `localStorage`와 `cookie` 모두 정상 동작 | Safari ITP로 저장소가 만료되어도 FIFO로 고아 메모 누적 없음 |
| 인앱 브라우저 | 외부 브라우저로 리다이렉트 | 공통 정책 참고 |
| 시크릿/프라이빗 모드 | 브라우저 종료 시 저장소 초기화 | 세션 종료 후 소유권 상실 |
| PC와 모바일 교차 사용 | 기기별 UUID가 달라 교차 수정 불가 | 회원가입 없는 구조의 한계로 수용 |

## 메모 소스와 저장 방식

커뮤니티 메모는 원본 소스를 그대로 벽에 붙이는 데이터가 아니라, 게시 전 편집 캔버스에서 완성된 최종 이미지
스냅샷을 벽에 부착하는 데이터이다.

프론트는 빈 캔버스에서 직접 작성하거나 갤러리 결과물을 불러온 뒤, 그림 그리기, 글씨 쓰기, 색칠, 텍스트박스,
스티커, 프레임 등 편집을 적용한다. 게시 시점에는 이 편집 결과를 최종 원본 이미지와 썸네일 이미지로 export해
기존 Files API로 업로드한다.

백엔드는 편집 도구의 내부 구조를 해석하지 않는다. OCR, 커뮤니티 벽 렌더링, 상세 보기, 후속 외부 공유의
기준은 MinIO에 저장된 커뮤니티 게시용 최종 이미지이다. `decoration`은 프론트가 다시 편집 화면을 열거나 상태를
복원하기 위한 보조 JSON이다.

| sourceType | 설명 | 요청 식별자 | 저장 방식 |
| --- | --- | --- | --- |
| `DIRECT` | 빈 캔버스에서 직접 작성, 드로잉, 텍스트박스, 색칠 등을 거쳐 만든 최종 게시 이미지 | `originalFileId`, `thumbnailFileId` | `community_memo.body_image_url`에 최종 원본 이미지 object key 저장, `community_memo.thumbnail_image_url`에 썸네일 object key 저장 |
| `GALLERY` | 갤러리 결과물을 출처로 불러와 그대로 또는 추가 편집 후 만든 최종 게시 이미지 | `sourceGalleryId`, `originalFileId`, `thumbnailFileId` | `community_memo.artifact_id`에 원본 artifact 연결, 최종 게시 이미지는 `body_image_url`과 `thumbnail_image_url`에 별도 저장 |

원본 URL과 썸네일 URL을 모두 응답하기 위해 `community_memo.thumbnail_image_url` 컬럼을 추가한다. 이 컬럼은
커뮤니티 게시용 썸네일 object key를 저장하며, 원본 갤러리 artifact의 썸네일과는 별개이다.

### 게시용 이미지와 원본 소스의 구분

- `artifact_id`는 갤러리에서 가져온 경우 원본 출처를 추적하기 위한 값이다.
- `body_image_url`은 커뮤니티에 실제 게시되는 최종 원본 이미지 object key이다.
- `thumbnail_image_url`은 커뮤니티 목록, 공유 미리보기, 가벼운 렌더링에 사용할 썸네일 이미지 object key이다.
- DIRECT 메모는 `artifact_id = null`이다.
- GALLERY 메모는 `artifact_id`로 원본 artifact를 참조하지만, 벽에 보여주는 이미지는 별도 업로드된 최종 게시 이미지이다.
- 갤러리 원본 artifact, subtype row, 원본 MinIO 파일은 커뮤니티 게시나 삭제로 수정하지 않는다.
- 같은 갤러리 결과물을 여러 번 게시하면 각 게시물은 서로 다른 최종 게시 이미지와 썸네일을 가질 수 있다.

### 직접 작성 메모 게시 이미지 업로드

직접 작성 메모는 기존 파일 공통 컴포넌트를 사용해 최종 원본 이미지와 썸네일 이미지를 업로드한다.

1. 프론트는 사용자가 완성한 편집 캔버스를 최종 원본 이미지로 export한다.
2. 프론트는 같은 결과를 목록과 후속 공유 미리보기에 적합한 썸네일 이미지로 export한다.
3. `POST /api/v1/files/presign`에 `purpose = COMMUNITY`로 원본 이미지 업로드 URL을 요청한다.
4. 프론트는 원본 이미지를 MinIO에 업로드하고 `POST /api/v1/files/{fileId}/confirm`으로 확정한다.
5. 같은 방식으로 썸네일 이미지를 업로드하고 confirm한다.
6. 커뮤니티 메모 생성 API에는 `sourceType = DIRECT`, `originalFileId`, `thumbnailFileId`, 배치 정보, 편집 상태 JSON을 전달한다.

커뮤니티 생성 API는 업로드 완료 상태이고 요청 UUID가 소유한 `COMMUNITY` 파일만 게시 이미지로 사용할 수 있다.
원본 이미지와 썸네일 이미지는 서로 다른 파일이어야 하며, 둘 다 `UPLOADED` 상태여야 한다.

### 갤러리 결과물 기반 게시

갤러리 결과물을 커뮤니티에 게시할 때도 최종 게시 이미지와 썸네일 이미지를 별도로 업로드한다. 원본
`artifact`는 출처 추적용으로만 연결한다.

- 사용자는 갤러리 결과물을 그대로 벽에 붙일 수 있다.
- 사용자는 갤러리 결과물에 데코레이션을 추가한 뒤 벽에 붙일 수 있다.
- 사용자가 갤러리 결과물을 그대로 붙이는 경우에도 프론트는 게시용 최종 이미지와 썸네일을 export해 업로드한다.
- 같은 갤러리 결과물을 여러 번 붙일 수 있다.
- 같은 원본 결과물을 한 번은 그대로, 한 번은 다른 데코레이션으로 꾸며서 붙일 수 있다.
- 갤러리 항목 삭제, 커뮤니티 게시 복사본 삭제, FIFO 삭제는 원본 `artifact`와 원본 MinIO 파일을 삭제하지 않는다.
- 커뮤니티 게시 이미지와 썸네일은 커뮤니티 게시물의 스냅샷이므로 원본 artifact 변경이나 삭제와 분리된다.

### 이미지 URL 응답 정책

DB에는 커뮤니티 게시용 최종 원본 이미지 object key와 썸네일 이미지 object key를 저장한다. API 응답에서는
프론트가 바로 렌더링할 수 있도록 public URL을 함께 내려준다.

- `memoOriginalImageUrl`은 `community_memo.body_image_url`의 object key를 public URL로 변환한 값이다.
- `memoThumbnailImageUrl`은 `community_memo.thumbnail_image_url`의 object key를 public URL로 변환한 값이다.
- `memoImageUrl`이 기존 호환 필드로 필요하면 기본 렌더링용 대표 이미지로 유지하되, 원칙적으로 썸네일 URL을 가리킨다.
- 갤러리 게시 메모도 벽 렌더링과 후속 공유에는 artifact 대표 이미지가 아니라 커뮤니티 게시용 최종 이미지 URL을 사용한다.
- `artifactId`, `galleryContentKind`는 원본 출처 표시와 상세 정보 연결에만 사용한다.
- public URL 생성은 MinIO 파일 존재 확인이나 presigned URL 재발급 없이 설정값과 저장된 경로를 조합한다.

### 생성 요청 필드

커뮤니티 메모 생성 API는 직접 작성과 갤러리 기반 게시 모두 최종 게시 이미지 중심으로 처리한다.

공통 요청 필드:

- `sourceType`: `DIRECT` 또는 `GALLERY`
- `originalFileId`: 최종 원본 이미지 파일 UUID
- `thumbnailFileId`: 최종 썸네일 이미지 파일 UUID
- `positionX`
- `positionY`
- `zIndex`
- `rotationDeg`
- `decoration`: 프론트 편집 상태 JSON, 없으면 `{}`
- `clientText`: 텍스트박스 등 프론트가 구조적으로 알고 있는 원문 텍스트, 없으면 빈 값

`sourceType = GALLERY`인 경우 `sourceGalleryId`를 함께 전달한다. `sourceGalleryId`는 원본 출처 검증과
`artifact_id` 연결에만 사용하며, 실제 게시 이미지는 `originalFileId`와 `thumbnailFileId`로 저장한다.

`clientText`는 OCR 보조 입력으로 사용한다. 프론트가 텍스트박스 원문을 알고 있다면 반드시 포함하는 것을
권장한다. 백엔드는 OCR 결과와 `clientText`를 함께 모더레이션 입력으로 사용한다.

## 사용자 흐름

### 직접 작성 메모를 붙이는 흐름

1. 사용자가 커뮤니티 캔버스 존에 진입한다.
2. 프론트는 사용자의 익명 UUID를 확인하고, 없으면 신규 익명 사용자 UUID를 발급한다.
3. 사용자가 빈 편집 캔버스에서 자유 글쓰기, 드로잉, 색칠, 텍스트박스, 스티커, 프레임 등을 사용해 메모를 만든다.
4. 사용자는 대형 캔버스 벽의 원하는 위치를 선택한다.
5. 프론트는 편집이 끝난 결과를 최종 원본 이미지와 썸네일 이미지로 export한다.
6. 프론트는 파일 공통 API로 `COMMUNITY` 목적의 presigned URL을 발급받아 원본 이미지와 썸네일 이미지를 각각 업로드한다.
7. 프론트는 두 파일의 업로드 confirm을 완료한다.
8. 프론트는 `sourceType = DIRECT`, `originalFileId`, `thumbnailFileId`, 위치, 회전, z-index, 편집 상태 JSON을 포함해 메모 생성 API를 호출한다.
9. 서버는 최종 원본 이미지 기준으로 OCR/텍스트 모더레이션을 수행한다.
10. 부적절 콘텐츠가 감지되면 서버는 커뮤니티 벽에 게시하지 않고 차단 응답을 반환한다.
11. 통과하면 서버는 새 메모를 생성하고, 보이는 메모가 50개를 초과하면 가장 오래 부착된 메모부터 `expired`로 소프트 삭제한다.
12. 프론트는 생성 응답 또는 목록 재조회 결과로 벽을 다시 렌더링한다.

### 갤러리 결과물을 그대로 붙이는 흐름

1. 사용자가 커뮤니티 캔버스에서 갤러리를 연다.
2. 프론트는 내 갤러리 목록을 조회한다.
3. 사용자가 릴레이 드로잉, 오늘의 운세, 플립북, 무한 캔버스, 휴대폰 그리기 등 결과물 하나를 선택한다.
4. 프론트는 선택한 결과물을 편집 캔버스에 올리되 별도 편집 없이 게시 상태로 둔다.
5. 사용자는 벽의 원하는 위치를 선택한다.
6. 프론트는 게시 상태를 최종 원본 이미지와 썸네일 이미지로 export한다.
7. 프론트는 두 이미지를 `COMMUNITY` 목적 파일로 업로드하고 confirm한다.
8. 프론트는 `sourceType = GALLERY`, `sourceGalleryId`, `originalFileId`, `thumbnailFileId`, 위치, 회전, z-index, 빈 편집 상태 JSON을 포함해 메모 생성 API를 호출한다.
9. 서버는 요청 UUID가 해당 갤러리 항목의 소유자인지 확인한다.
10. 서버는 원본 artifact를 출처로 연결하되, 커뮤니티 벽에는 업로드된 최종 게시 이미지를 사용한다.
11. 서버는 최종 원본 이미지 기준으로 OCR/텍스트 모더레이션을 수행한다.
12. 통과하면 새 `community_memo`를 생성하고 50개 FIFO를 처리한다.
13. 프론트는 목록을 다시 조회해 벽을 렌더링한다.

### 갤러리 결과물을 꾸민 뒤 붙이는 흐름

1. 사용자가 갤러리에서 결과물을 선택한다.
2. 프론트는 선택한 결과물을 메모지 형태로 보여준다.
3. 사용자는 스티커, 테두리, 낙서, 색칠, 텍스트박스 등 편집 요소를 추가한다.
4. 사용자는 벽의 원하는 위치를 선택한다.
5. 프론트는 편집 결과를 최종 원본 이미지와 썸네일 이미지로 export한다.
6. 프론트는 두 이미지를 `COMMUNITY` 목적 파일로 업로드하고 confirm한다.
7. 프론트는 `sourceType = GALLERY`, `sourceGalleryId`, `originalFileId`, `thumbnailFileId`, 위치, 회전, z-index, 편집 상태 JSON을 포함해 메모 생성 API를 호출한다.
8. 서버는 원본 artifact는 변경하지 않고, 커뮤니티 게시물에만 출처 artifact와 최종 게시 이미지 object key를 저장한다.
9. 서버는 최종 원본 이미지 기준으로 OCR/텍스트 모더레이션을 수행한다.
10. 같은 갤러리 결과물을 다시 선택하면 다른 위치, 다른 편집 상태, 다른 최종 게시 이미지로 한 번 더 게시할 수 있다.

### 붙인 뒤 배치를 수정하는 흐름

1. 사용자가 벽에 붙은 메모를 선택한다.
2. 목록 또는 상세 응답의 `ownedByMe = true`인 경우 프론트는 수정과 삭제 UI를 제공한다.
3. 사용자는 위치, 회전, z-index를 수정할 수 있다.
4. 프론트는 수정된 배치 필드만 메모 수정 API로 전송한다.
5. 서버는 요청 UUID가 메모 작성자인지 확인한 뒤 전달받은 배치 필드만 갱신한다.
6. 게시된 이미지 스냅샷, 편집 상태 JSON, 원본 갤러리 artifact, 작성자, 최초 부착 시각은 수정하지 않는다.

게시 후 그림, 글씨, 텍스트박스, 스티커 등 시각적 내용을 다시 수정하고 새 최종 이미지로 교체하는 기능은 후속
범위로 둔다.

### 본인 메모를 삭제하는 흐름

1. 사용자가 본인 메모를 선택한다.
2. 프론트는 삭제 확인 UI를 제공한다.
3. 사용자가 삭제를 확정하면 프론트는 메모 삭제 API를 호출한다.
4. 서버는 요청 UUID가 메모 작성자인지 확인한다.
5. 서버는 메모를 하드 삭제하지 않고 `deleted_at`과 `deleted_reason = user_delete`를 기록한다.
6. 직접 작성 메모 이미지, 원본 artifact, MinIO 파일은 삭제하지 않는다.
7. 프론트는 목록을 다시 조회해 삭제된 메모를 벽에서 제거한다.

## 주요 기능

- 자유 글쓰기와 드로잉을 지원한다.
- 색칠, 텍스트박스, 스티커, 프레임 등 게시 전 편집 기능을 지원한다.
- 갤러리에서 릴레이 드로잉, 오늘의 운세, 플립북, 무한 캔버스 등 각 부스 결과물을 불러올 수 있다.
- 갤러리 결과물을 편집 없이 최종 게시 이미지로 export해 바로 붙일 수 있다.
- 갤러리 결과물에 편집 요소를 추가한 뒤 최종 게시 이미지로 export해 붙일 수 있다.
- 게임 완료 결과물은 갤러리에 자동 저장된다.
- 같은 갤러리 아이템을 여러 번 게시할 수 있다.
- 게시된 각 메모 복사본은 독립적으로 FIFO, 신고, 삭제 정책을 적용받는다.
- 게시된 메모의 벽 렌더링, 상세 보기, 후속 외부 공유 기준은 커뮤니티 게시용 최종 이미지 스냅샷이다.
- 편집 상태 JSON은 재편집을 위한 보조 데이터이며, 시각적 수정이 실제 반영되려면 새 최종 이미지와 썸네일을 업로드해야 한다.
- 사용자는 메모 부착 위치를 자유롭게 선택한다.
- 본인 메모는 소유권이 유효한 동안 배치 수정과 삭제가 가능하다.
- 편집 상태 수정과 최종 이미지 교체는 후속 범위로 둔다.
- 커뮤니티 게시 전 OCR/텍스트 모더레이션으로 부적절한 텍스트가 감지되면 게시 자체를 차단한다.
- 가려진 내 메모 찾기 기능을 제공한다.
- 타인 메모는 읽기와 터치 반응만 가능하며 수정 및 이동은 불가하다.
- 신고 기능을 제공한다.
- 신고 5회 누적 시 `is_hidden = true`로 자동 숨김 처리한다.
- 운영자는 백오피스에서 숨김 메모를 검토해 복원하거나 `deleted_reason = admin_removed`로 소프트 삭제한다.

## 조회 응답 정책

### 목록 조회

공용 벽 목록은 프론트가 추가 상세 조회 없이 벽을 기본 렌더링할 수 있도록 필요한 필드를 함께 반환한다.

조회 조건:

- `deleted_at IS NULL`
- `is_hidden = false`
- 정렬은 `z_index ASC`, 동률이면 `attached_at ASC`

대표 응답 필드:

- `memoUuid`
- `authorNickname`
- `sourceType`
- `memoImageUrl`
- `memoOriginalImageUrl`
- `memoThumbnailImageUrl`
- `positionX`
- `positionY`
- `zIndex`
- `rotationDeg`
- `ownedByMe`
- `attachedAt`

목록 응답에는 작성자 UUID를 노출하지 않는다. 프론트가 내 메모 여부를 쉽게 판단할 수 있도록 요청자의
`Anonymous-User-UUID`와 메모 작성자가 같으면 `ownedByMe = true`를 반환한다.

### 상세 조회

상세 조회는 목록 필드에 더해 메모 관리와 편집에 필요한 자세한 정보를 반환한다.

대표 응답 필드:

- `decoration`
- `artifactId`
- `galleryContentKind`
- `moderationStatus`
- `reportCount`
- `createdAt`
- `updatedAt`

### 수정 요청

1차 메모 수정은 본인 메모에 한해 배치 정보만 부분 수정 방식으로 처리한다. 프론트가 보낸 필드만 갱신하고,
누락된 필드는 기존 값을 유지한다.

수정 가능 필드:

- `positionX`
- `positionY`
- `zIndex`
- `rotationDeg`

수정 불가 필드:

- 게시된 최종 원본 이미지
- 게시된 썸네일 이미지
- `decoration`
- 갤러리에서 가져온 원본 결과물
- 연결된 `artifact`
- 작성자
- `attachedAt`

`decoration`, `originalFileId`, `thumbnailFileId`를 통한 시각적 내용 재수정과 이미지 교체는 후속 범위로 둔다.
이미지 교체 기능을 추가하더라도 원본 갤러리 artifact는 변경하지 않는다.

## AI 모더레이션

커뮤니티 메모는 공용 벽에 노출되기 전에 OCR/텍스트 모더레이션을 통과해야 한다. 부적절한 텍스트가 감지되면
커뮤니티 게시물 생성을 완료하지 않고 게시 자체를 차단한다.

검사 기준 이미지는 프론트가 편집을 끝낸 뒤 업로드한 커뮤니티 게시용 최종 원본 이미지이다. 빈 캔버스에서 직접
작성했는지, 갤러리 결과물을 불러와 수정했는지는 검사 기준에 영향을 주지 않는다.

기본 정책은 게시 전 동기 차단이다. 즉, Spring BE가 커뮤니티 메모를 INSERT하기 전에 FastAPI 모더레이션
서비스를 호출하고, 통과한 경우에만 `community_memo`를 생성한다. 이 정책은 부적절한 이미지가 짧은 시간이라도
공용 벽이나 후속 외부 공유에 노출되는 것을 막기 위한 기본값이다.

FastAPI OCR/모더레이션 응답 시간이 사용자 경험을 해칠 정도로 길거나 장애 가능성이 크면, 후속 구현에서
`pending` 미노출 방식을 사용할 수 있다. 이 대안에서도 메모는 검수 통과 전까지 목록, 상세, 공유에 노출하지
않는다.

### 검사 파이프라인

1. 프론트가 최종 원본 이미지와 썸네일 이미지를 `COMMUNITY` 목적 파일로 업로드하고 confirm한다.
2. 프론트가 커뮤니티 메모 생성 API를 호출한다.
3. 서버는 생성 요청의 최종 원본 이미지 URL 또는 object key를 모더레이션 대상으로 사용한다.
4. Naver CLOVA OCR로 최종 원본 이미지를 분석해 텍스트를 추출한다.
5. 프론트가 텍스트박스 원문을 `clientText` 필드로 보내면 OCR 결과와 함께 검사 입력으로 사용한다.
6. 추출 텍스트와 보조 텍스트를 Unsmile 또는 동등 수준의 한국어 혐오 표현 분류 모델에 전달한다.
7. 여성/가족 혐오, 남성 혐오, 성소수자 혐오, 인종/국적 혐오, 연령 혐오, 지역 혐오, 종교 혐오, 기타 혐오,
   악플/욕설 등 카테고리를 분류한다.

### 처리 정책

- 일반 텍스트와 드로잉 도구로 그려 쓴 글자는 모두 OCR 대상이다.
- 텍스트박스는 최종 이미지에 렌더링되어야 하며, 가능하면 원문 텍스트도 별도 보조 입력으로 전달한다.
- 이미지 내용 자체, 그림, 일러스트의 시각적 표현은 판정하지 않는다.
- OCR로 추출된 텍스트만 혐오 표현 분류 대상이다.
- 순수 그림은 OCR 결과가 비어 자연스럽게 통과된다.
- 플립북 등 움직이는 결과물도 커뮤니티 게시 시점에는 프론트가 정지된 최종 게시 이미지 스냅샷을 함께 업로드해야 한다.
- 부적절 표현이 감지되면 커뮤니티 메모를 visible 상태로 생성하지 않는다.
- 차단 응답은 프론트가 “부적절한 표현이 감지되어 게시할 수 없어요” 같은 안내를 표시할 수 있도록 명확한 실패 메시지를 제공한다.
- 차단된 업로드 파일은 즉시 삭제하지 않는다. 파일 정리는 별도 파일 생명주기 정책 또는 운영 배치에서 처리한다.
- 모더레이션 서비스 장애, 타임아웃, OCR 실패 시에는 게시를 허용하지 않는 fail-closed 정책을 기본값으로 한다.
- fail-closed로 인한 사용자 경험 손상이 크다고 판단되면 게시 허용이 아니라 pending 미노출 방식으로 전환한다.

### DB 저장과 상태 전이

- 모더레이션 통과 후 `community_memo`를 생성한다.
- 생성되는 메모는 `moderation_status = allowed`로 시작하는 것을 원칙으로 한다.
- 차단된 요청은 커뮤니티 벽에 노출되는 `community_memo` row를 만들지 않는다.
- 차단 이력을 운영 분석에 남겨야 한다면 별도 moderation attempt 로그 또는 감사 로그를 후속으로 설계한다.
- 통과한 메모에 대해서도 OCR 원문 텍스트를 보존해야 한다면 `community_memo.ocr_text`에 평문으로 저장한다.
- 분류 결과 라벨, 점수, 모델 메타데이터를 보존해야 한다면 `community_memo.ocr_categories`에 JSON 문자열로 저장한다.
- 검사 완료 시각은 `moderation_checked_at`에 기록한다.
- 신고 5회 누적 자동 숨김은 게시 후 사용자 신고 정책이므로 `moderation_status`를 변경하지 않고 `is_hidden = true`, `hidden_reason = report_threshold`로 처리한다.
- 운영자가 게시 후 숨김 메모를 복원하면 `is_hidden = false`로 되돌리며, `moderation_status`는 기존 값을 유지한다.

### pending 미노출 대안

FastAPI 응답 시간이 길어 동기 차단이 어렵다면 다음 대안을 사용할 수 있다.

1. 커뮤니티 메모 생성 요청 시 `community_memo` row를 먼저 만들되 `moderation_status = pending`, `is_hidden = true`로 저장한다.
2. 목록, 상세, 공유 조회는 `moderation_status = allowed`, `is_hidden = false`, `deleted_at IS NULL`인 메모만 노출한다.
3. 비동기 워커가 FastAPI 모더레이션을 호출한다.
4. 통과하면 `moderation_status = allowed`, `is_hidden = false`, `moderation_checked_at = now`로 전환한다.
5. 차단이면 `moderation_status = blocked`, `is_hidden = true`, `hidden_reason = ai_moderation`, `hidden_at = now`, `moderation_checked_at = now`로 유지한다.

이 방식은 사용자 요청을 빠르게 끝낼 수 있지만, 생성 직후 바로 벽에 붙는 경험이 아니라 “검수 중” 상태가
생긴다. 그래도 부적절 콘텐츠가 먼저 노출되는 방식은 사용하지 않는다.

### 모더레이션 호출 흐름

- 모더레이션은 외부 REST API로 사용자나 백오피스에 노출하지 않는다.
- Spring BE는 기본 정책에서 `community_memo` INSERT 전에 사내망 FastAPI 모더레이션 서비스의 `POST /check`를 호출한다.
- 요청 body 예시는 `{ "imageUrl": "...", "clientText": "...", "sourceType": "DIRECT" }`이다.
- 모더레이션 통과 응답을 받은 경우에만 `community_memo`를 생성한다.
- 차단 응답을 받은 경우에는 `community_memo`를 생성하지 않고 API 실패 응답을 반환한다.
- pending 미노출 대안을 선택한 경우에만 INSERT 후 비동기 워커가 FastAPI를 호출한다.
- FastAPI는 사용자 클라이언트와 백오피스가 직접 호출하지 않으며, VPC/사설망에서만 접근 가능하다.

### 신고와 병행

- AI 모더레이션은 게시 전 차단이고, 신고 5회 누적은 게시 후 숨김이다.
- 게시 전 AI 차단은 `community_memo`를 visible 상태로 만들지 않는다.
- 게시 후 신고 5회 누적은 `is_hidden = true`, `hidden_reason = report_threshold`로 전환한다.
- 백오피스 검토 큐에서 사유별 분리 조회가 가능해야 한다.

### 오탐과 운영 모니터링

- 게시 전 차단 오탐 또는 게시 후 자동 숨김 오탐이 발생할 수 있다.
- 별도 사용자 이의 제기 채널은 두지 않는다.
- 게시 전 차단 오탐이 발생할 수 있으므로 차단 로그는 UUID, 최종 원본 이미지 object key, OCR 추출 텍스트, 보조 텍스트, 감지 카테고리, 요청 시각, 검사 완료 시각, 검사 지연 시간을 포함한다.
- 게시 후 신고로 숨김 처리된 메모는 운영자가 백오피스에서 복원하면 다시 노출된다.
- 오탐 비율은 OCR과 혐오 표현 분류 모델 임계값 조정에 참고한다.

## 후속 외부 공유 정책 초안

커뮤니티 게시물 외부 공유는 1차 CRUD/FIFO 이후 후속 범위로 둔다. 공유를 구현할 때의 기준은 갤러리 원본이나
편집 JSON이 아니라 커뮤니티에 게시된 최종 이미지 스냅샷이다.

- 공유 대상은 visible 상태의 커뮤니티 메모이다.
- `deleted_at IS NOT NULL`인 메모는 공유할 수 없다.
- `is_hidden = true`인 메모는 공유할 수 없다.
- 게시 전 모더레이션에서 차단된 메모는 공유 대상이 아니다.
- 공유 응답과 공유 미리보기에는 `memoOriginalImageUrl`과 `memoThumbnailImageUrl`을 사용할 수 있다.
- OpenGraph, 카카오 공유, 링크 미리보기에는 썸네일 이미지를 우선 사용한다.
- 공유 상세 페이지에서 원본 이미지를 보여줄 때도 현재 메모의 visible 상태를 다시 확인한다.
- MinIO public URL을 외부에 직접 영구 노출하면 숨김/삭제 후에도 URL을 아는 사람이 접근할 수 있는 리스크가 있다.
- 권한 통제가 필요하면 공유 페이지 또는 공유 API가 백엔드를 경유해 visible 상태를 확인한 뒤 이미지를 제공한다.
- 커뮤니티 메모 삭제, 신고 숨김, 운영자 삭제가 발생하면 공유 페이지에서도 더 이상 노출하지 않는다.

## 신고 정책

| 항목 | 정책 |
| --- | --- |
| 신고 대상 | 캔버스 벽에 부착된 모든 메모 |
| 신고 방식 | 메모 터치 후 신고 버튼 노출, 신고 사유 선택 |
| 신고 사유 | 부적절 콘텐츠, 스팸, 그 외 |
| 중복 신고 방지 | 동일 UUID로 같은 메모 중복 신고 불가 |
| 자동 숨김 기준 | 신고 5회 누적 |
| 숨김 방식 | DB 삭제가 아니라 `is_hidden = true`로 전환 |
| 본인 메모 신고 | 불가, 본인은 직접 삭제 가능 |

### 숨김 후 처리

- 운영자는 숨김된 메모를 백오피스에서 검토한다.
- 악성 신고로 판단되면 `is_hidden = false`로 복원한다.
- 실제 부적절하면 `deleted_at`, `deleted_reason = admin_removed`로 소프트 삭제한다.
- 복원 시 캔버스가 50개를 초과할 수 있으나 즉시 다른 메모를 삭제하지 않는다.
- 다음 새 메모 부착 시 FIFO가 초과분을 정리한다.
- 운영자 검토 이력은 `reviewed_at`, `reviewed_by`, 복원/삭제 결정을 별도 감사 로그에 남긴다.

## 삭제 사유

| 값 | 의미 |
| --- | --- |
| `expired` | 갯수 한도 50개 초과로 FIFO 자동 소프트 삭제 |
| `admin_removed` | 운영자 검토 후 부적절 콘텐츠 소프트 삭제 |
| `user_delete` | 본인 직접 소프트 삭제 |

- 숨김 상태 메모는 FIFO 삭제 경로를 타지 않는다.
- 숨김 상태 메모는 운영자 검토 후 삭제될 때만 `admin_removed`로 기록된다.
- 백오피스 통계에서 삭제 사유별 비율을 확인할 수 있어야 한다.

## 인터랙션 연출

- 메모 부착 시 점착 사운드와 부착감을 제공한다.
- 터치 시 종이 팔락임을 연출한다.
- 그림자와 모서리 흔들림으로 종이의 깊이감을 표현한다.
- 겹쳐 붙인 메모의 레이어감과 그림자를 표현한다.
- 가까이 가면 메모가 살짝 들썩이며 읽기 가능 상태를 암시한다.
- 이동하거나 떼어낼 때 종이가 벗겨지는 사운드를 제공한다.

## 결과물 처리

커뮤니티는 결과물이 곧 공간이 되는 구조이다. 별도 갤러리 없이 벽 자체가 전시 공간이다. 갯수 기반 FIFO로
캔버스는 항상 최대 50개의 메모로 풍성한 상태를 유지하며, 새 메모가 부착될 때 오래된 메모가 순차적으로
물러난다.
