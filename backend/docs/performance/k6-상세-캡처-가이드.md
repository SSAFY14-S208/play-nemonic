# k6 상세 결과 캡처 가이드

이 문서는 백엔드 성능 최적화 결과를 포트폴리오에 넣을 때, k6 터미널 출력과 before / after 표를 어떻게 남길지 정리한 가이드입니다.

## 왜 상세 출력이 필요한가

한 줄 요약은 빠르게 확인하기 좋지만, 포트폴리오 증거로는 약합니다.

k6 상세 출력에는 같은 테스트 안에서 latency, throughput, 실패율, check 성공률이 함께 보입니다. 그래서 “빨라졌다”가 아니라 “같은 조건에서 p95가 줄고 실패율이 유지됐다”를 보여줄 수 있습니다.

## 캡처해야 하는 지표

| 지표 | 캡처 이유 |
| --- | --- |
| `http_req_duration p(95)` | 대부분의 사용자가 체감하는 지연 시간 비교 |
| `http_req_duration p(99)` | 긴 꼬리 지연 시간, 최악 구간 개선 여부 확인 |
| `http_reqs` rate | 초당 처리량 비교 |
| `http_req_failed` | 실패율이 증가하지 않았는지 확인 |
| `checks` | 응답 status와 response contract가 정상인지 확인 |
| `iterations` | 테스트가 중간에 끊기지 않고 완료됐는지 확인 |

## 캡처 화면 기준

터미널 캡처에는 아래 영역이 같이 보이도록 합니다.

```text
=== 갤러리 목록 조회 k6 부하 테스트 ===
endpoint=gallery_list p95=... ms rps=... failed=...%

--- k6 상세 지표 ---
checks..........................: 100.00% ... passed 0 failed
http_req_duration...............: avg=... min=... med=... max=... p(90)=... p(95)=... p(99)=...
http_req_failed.................: 0.00% 0 failed ... ok
http_reqs.......................: ... .../s
iterations......................: ... .../s
```

## before / after 표 템플릿

각 트러블 슈팅 문서에는 아래 형식으로 k6 결과를 정리합니다.

| API | 기준 | VUS | Duration | p95 | p99 | RPS | 실패율 | 비고 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 갤러리 목록 조회 | Before | 20 | 30s | 000.00ms | 000.00ms | 00.00/s | 0.00% | 최적화 전 커밋 |
| 갤러리 목록 조회 | After | 20 | 30s | 000.00ms | 000.00ms | 00.00/s | 0.00% | 최적화 후 커밋 |

계산식은 아래처럼 적으면 좋습니다.

```text
p95 개선율 = (Before p95 - After p95) / Before p95 * 100
p99 개선율 = (Before p99 - After p99) / Before p99 * 100
RPS 개선율 = (After RPS - Before RPS) / Before RPS * 100
```

## 트러블 슈팅별 실행 명령

### 트러블 슈팅 1. 운세 생성 외부 I/O 트랜잭션 분리

```bash
k6 run \
  -e BASE_URL=http://localhost:8080/api/v1 \
  -e RAMP_UP=5s \
  -e DURATION=20s \
  -e RAMP_DOWN=5s \
  -e VUS=3 \
  -e P95_THRESHOLD_MS=10000 \
  backend/docs/performance/01-운세-생성-외부-io-트랜잭션-분리/k6/01-운세-생성-k6.js
```

이 최적화는 k6 결과와 함께 운세 생성 전용 HikariCP 커넥션 점유 시간 그래프를 같이 제시합니다. k6는 HTTP 체감 latency를 보여주고, HikariCP 그래프는 GMS/MinIO를 트랜잭션 밖으로 뺀 이유를 보여줍니다.

### 트러블 슈팅 2. 문의 답변 SMTP I/O 트랜잭션 분리

```bash
k6 run \
  -e BASE_URL=http://localhost:8080/api/v1 \
  -e ADMIN_TOKEN=$ADMIN_TOKEN \
  -e RAMP_UP=5s \
  -e DURATION=20s \
  -e RAMP_DOWN=5s \
  -e VUS=5 \
  -e P95_THRESHOLD_MS=5000 \
  backend/docs/performance/02-문의-답변-메일-io-트랜잭션-분리/k6/02-문의-답변-k6.js
```

이 최적화는 k6 결과와 함께 문의 답변 전용 HikariCP 커넥션 점유 시간 그래프를 같이 제시합니다. k6는 HTTP 체감 latency를 보여주고, HikariCP 그래프는 SMTP 발송을 트랜잭션 밖으로 뺀 이유를 보여줍니다.

### 트러블 슈팅 3. 갤러리 목록 조회 쿼리 최적화

```bash
k6 run \
  -e BASE_URL=http://localhost:8080/api/v1 \
  -e USER_UUID=$USER_UUID \
  -e RAMP_UP=5s \
  -e DURATION=30s \
  -e RAMP_DOWN=5s \
  -e VUS=20 \
  backend/docs/performance/03-갤러리-목록-조회-쿼리-최적화/k6/03-갤러리-목록-조회-k6.js
```

갤러리는 seed 데이터가 중요합니다. 갤러리 row가 거의 없는 사용자로 실행하면 API 경로가 정상인지 확인하는 smoke test로는 충분하지만, 쿼리 최적화 효과를 보여주는 수치로는 약합니다.

### 트러블 슈팅 5. 무한캔버스 요소 적용 로직 최적화

무한캔버스 요소 적용 로직은 HTTP API 부하보다 서버 내부 자료구조 적용 비용이 핵심이므로, 아래 synthetic benchmark 결과를 사용합니다.

```bash

```

## 결과 파일

k6 실행 후 raw 결과는 아래 경로에 저장됩니다.

```text
backend/docs/performance/*/k6/results/*.json
backend/docs/performance/*/k6/results/*.md
```

포트폴리오에는 raw JSON 전체를 붙이기보다 다음 순서로 보여주는 편이 좋습니다.

1. 문제 상황과 병목 원인
2. 적용한 최적화
3. k6 터미널 상세 캡처
4. before / after 표
5. p95, p99, RPS 그래프
6. 운영에서 확인할 모니터링 지표

## 주의할 점

- before와 after는 같은 seed 데이터, 같은 VUS, 같은 duration으로 실행합니다.
- 로컬 테스트 수치는 운영 실측 수치가 아니라 통제된 환경의 비교 지표로 표시합니다.
- 실패율이 0%가 아니면 latency 개선 수치보다 실패 원인을 먼저 확인합니다.
- 외부 API, SMTP, MinIO처럼 네트워크 I/O가 섞이는 테스트는 stub 또는 로컬 테스트 환경을 고정해야 비교가 깨끗합니다.
