# 네모닉(Nemonic) 포팅 메뉴얼

이 문서는 네모닉 서비스를 새로운 환경에 배포하기 위해 필요한 최소 요구사항과 절차를 정리합니다.

서비스는 네 개의 독립 컴포넌트로 구성됩니다.

- **Backend** — Spring Boot 기반 REST/WebSocket 서버
- **Frontend** — Next.js 기반 SPA/SSR
- **AI** — FastAPI 기반 콘텐츠 모더레이션 서버
- **Infrastructure** — Docker Compose 기반 운영 인프라(리버스 프록시 / DB / 캐시 / 객체 스토리지 / 모니터링 / 로깅)

---

## 1. 최소 요구사항

### 1.1 호스트 환경

| 항목 | 최소 사양 |
| --- | --- |
| OS | Linux / Windows / macOS (Docker 가 실행 가능한 환경) |
| CPU | 4 vCPU |
| RAM | 8 GB (모니터링·로깅 스택 포함 시 16 GB 권장) |
| Disk | 50 GB 이상 (DB·객체 스토리지·로그 인덱스 포함) |
| Network | 공인 도메인 + TLS 인증서 |

OS 별 권장 사항:

- **Linux (Ubuntu 22.04 / 24.04 LTS)** — 운영 환경 표준. 모든 컨테이너가 Linux 기반이므로 가장 안정적이며 성능 오버헤드가 없음.
- **Windows 10/11, Windows Server** — Docker Desktop(WSL2 백엔드) 또는 Docker Engine on WSL2 사용. 로컬 개발/소규모 운영에 가능. 단, 컨테이너는 WSL2 내부 Linux 커널에서 실행됨.
- **macOS** — Docker Desktop 사용. 로컬 개발에 적합. 운영 용도로는 비권장.

### 1.2 필수 소프트웨어

| 소프트웨어 | 최소 버전 |
| --- | --- |
| Docker | 20.10 (BuildKit 지원) — Linux는 Docker Engine, Windows/Mac은 Docker Desktop |
| Docker Compose | 2.20 (plugin 형태) |
| Git | 2.25 |

### 1.3 커널 파라미터 (OpenSearch 사용 시)

**Linux**

```bash
sudo sysctl -w vm.max_map_count=262144
echo "vm.max_map_count=262144" | sudo tee -a /etc/sysctl.conf
```

**Windows (WSL2)**

WSL2 가 사용하는 Linux 커널에 적용해야 합니다. `%UserProfile%\.wslconfig` 에 다음을 추가하고 `wsl --shutdown` 으로 재시작합니다.

```ini
[wsl2]
kernelCommandLine = "sysctl.vm.max_map_count=262144"
```

또는 WSL 셸 안에서 `sudo sysctl -w vm.max_map_count=262144` 를 실행합니다(재부팅 시 초기화).

## 3. 서비스 아키텍처

모든 컴포넌트는 단일 호스트의 Docker 네트워크 위에서 동작하며, 외부에는 Nginx만 노출됩니다.

```
[Internet]
    │  443
    ▼
┌──────────────────────────────────────────────┐
│ Nginx (TLS 종단 + 라우팅)                     │
└──────────────────────────────────────────────┘
    │
    ├── /              → Frontend (Next.js)
    ├── /api/, /ws/    → Backend (Spring Boot)
    ├── /minio/        → MinIO 콘솔
    ├── /grafana/      → Grafana (BasicAuth)
    └── /_dashboards/  → OpenSearch Dashboards (BasicAuth)

[내부 전용]
- Backend → AI (HTTP, 모더레이션 검사)
- Backend → PostgreSQL / Redis / MinIO
- 모든 컨테이너 stdout → 로깅 파이프라인
```

## 5. 환경 변수

`.env` 파일에 작성하여 Docker Compose가 자동으로 로드하도록 합니다. 모든 시크릿은 새로 발급해야 합니다.

### 5.1 공통

```env
DOMAIN=<your-domain.example.com>
SPRING_PROFILES_ACTIVE=prod

```

### 5.2 Backend

```env
# 데이터베이스
DB_URL=jdbc:postgresql://postgres:5432/<db_name>
DB_NAME=<db_name>
DB_USERNAME=<db_user>
DB_PASSWORD=<secret>

# 서버

# Redis

MINIO_ACCESS_KEY=<access-key>

MINIO_BUCKET=<bucket-name>

ADMIN_BOOTSTRAP_EMAIL=<email>

# AI 모더레이션 서버 연동

# 외부 LLM 게이트웨이 (선택)
```

## 6. 로컬 개발 환경 기동

개발자 PC에서 전체 스택을 한 번에 띄워 동작을 확인하는 절차입니다. 외부 도메인·TLS 없이 `localhost` 만으로 동작합니다.

### 6.1 사전 준비

- JDK 21, Node.js 20 + pnpm 10, Python 3.12, Docker / Docker Compose 설치
- 저장소 클론 후 각 컴포넌트별로 의존성 설치 (아래 단계에 포함)

### 6.2 단계별 기동 순서

#### Step 1. 의존 인프라 (PostgreSQL / Redis / MinIO)

```bash
cd backend
docker compose -f docker-compose.local.yml up -d

# Windows PowerShell 헬퍼
# powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\local-up.ps1
```

기동 후 확인:

- PostgreSQL: `localhost:5432`
- Redis: `localhost:6379`
- MinIO API: `http://localhost:9000` / 콘솔: `http://localhost:9001`

#### Step 2. AI 모더레이션 서버 (선택)

커뮤니티 신고/모더레이션 기능을 테스트할 경우에만 필요합니다. 기능을 사용하지 않으려면 Backend `.env` 에서 `COMMUNITY_MODERATION_ENABLED=false` 로 두고 이 단계를 건너뜁니다.

```bash
cd ai/moderation-server
python -m venv .venv

# Linux / macOS
./.venv/bin/pip install -r requirements.txt
cp .env.example .env
./.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload

# Windows PowerShell
.\.venv\Scripts\pip.exe install -r requirements.txt
copy .env.example .env
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

> 첫 기동 시 HuggingFace에서 모델을 자동 다운로드합니다(30~60초).

확인: `http://localhost:8000/docs` (Swagger UI)

#### Step 3. Backend

```bash
cd backend

# .env 작성 — 최소 시크릿만 채우기
cp .env.example .env
# 필수: ADMIN_JWT_SECRET (openssl rand -base64 32)
# 선택: ADMIN_BOOTSTRAP_ENABLED=true 로 두면 최초 관리자 계정 자동 생성

# 실행
./gradlew bootRun                  # Linux / macOS
gradlew.bat bootRun                # Windows
```

확인: `http://localhost:8080/actuator/health` → `{"status":"UP"}`

#### Step 4. Frontend

```bash
cd frontend

# 로컬용 .env.local 작성
cat > .env.local <<'EOF'
NEXT_PUBLIC_API_URL=http://localhost:8080/api
NEXT_PUBLIC_WEBSOCKET_URL=ws://localhost:8080/ws
EOF

pnpm install --frozen-lockfile
pnpm dev
```

확인: `http://localhost:3000`

### 6.3 환경 변수 최소 셋 (로컬)

`.env.example` 의 기본값으로 대부분 동작하며, 다음만 값을 채우면 됩니다.

**backend/.env**

```env
ADMIN_JWT_SECRET=<openssl rand -base64 32>
ADMIN_BOOTSTRAP_ENABLED=true
ADMIN_BOOTSTRAP_LOGIN_ID=admin
ADMIN_BOOTSTRAP_PASSWORD=admin1234!
ADMIN_BOOTSTRAP_NICKNAME=admin
ADMIN_BOOTSTRAP_EMAIL=admin@example.com

# AI 모더레이션 미사용 시
COMMUNITY_MODERATION_ENABLED=false
# 사용 시
# COMMUNITY_MODERATION_BASE_URL=http://localhost:8000
```

**frontend/.env.local**

```env
NEXT_PUBLIC_API_URL=http://localhost:8080/api
NEXT_PUBLIC_WEBSOCKET_URL=ws://localhost:8080/ws
```

**ai/moderation-server/.env** — 기본값 그대로 사용 가능

### 6.4 종료

```bash
# 인프라 컨테이너 종료 (데이터는 볼륨에 보존)
cd backend
docker compose -f docker-compose.local.yml down

# 완전 초기화 (DB·MinIO 데이터 삭제)
docker compose -f docker-compose.local.yml down -v
```

Backend / Frontend / AI 프로세스는 각 터미널에서 `Ctrl + C` 로 종료합니다.

## 7. 빌드 및 배포 (운영용)

운영 환경에 배포할 때 사용하는 컨테이너 이미지 빌드와 일괄 기동 절차입니다.

### 7.1 컴포넌트 이미지 빌드

**Backend**

```bash
cd backend
./gradlew bootJar
docker build -f Dockerfile -t nemonic/app:latest .
```

**Frontend**

```bash
cd frontend
docker build -f Dockerfile -t nemonic/frontend:latest .
```

**AI 모더레이션 서버**

```bash
cd ai/moderation-server
docker build -t nemonic/moderation-server:latest .
```

### 7.2 운영 스택 일괄 기동

각 컴포넌트 이미지가 사전에 빌드되어 있거나 컨테이너 레지스트리에서 pull 가능한 상태여야 합니다.

```bash
# 운영 스택 (Nginx + Backend + Frontend + AI + DB + Redis + MinIO)
docker compose -f docker-compose.prod.yml up -d

# 모니터링 (Prometheus + Grafana + exporters) — 선택
docker compose -f docker-compose.monitoring.yml up -d

# 로깅 (Fluent Bit + Kafka + Logstash + OpenSearch + Dashboards) — 선택
docker compose -f docker-compose.logging.yml up -d
```

## 8. 배포 사전 준비

1. 도메인 DNS A 레코드를 서버 IP로 설정
2. TLS 인증서 발급 (Let's Encrypt 등) → Nginx가 참조할 경로에 배치
3. 데이터 영속화 디렉터리 생성 및 권한 설정 (`postgres`, `redis`, `minio`, `opensearch`, `prometheus`, `grafana` 등)
4. Docker 공유 네트워크 생성
5. BasicAuth 보호 경로(Grafana / OpenSearch Dashboards) 사용 시 `htpasswd` 파일 생성
6. `.env` 작성 (모든 시크릿은 무작위 생성)
7. 컨테이너 이미지 빌드 또는 레지스트리에서 pull
8. `docker compose up -d` 로 기동
9. 관리자 계정 1회 부트스트랩 (`ADMIN_BOOTSTRAP_ENABLED=true` → 기동 후 `false`)

## 9. 데이터베이스 마이그레이션

- 마이그레이션 도구: **Flyway**
- 위치: `backend/src/main/resources/db/migration/V*.sql`
- 백엔드 부팅 시 자동 적용 (`spring.flyway.enabled=true`)
- Hibernate DDL: `validate` (스키마 불일치 시 부팅 실패)
- 비활성화하려면 `FLYWAY_ENABLED=false`

## 10. 외부 서비스 (선택)

기능 사용 여부에 따라 발급/구성합니다.

| 서비스 | 용도 | 필수 여부 |
| --- | --- | --- |
| TLS 인증서(Let's Encrypt 등) | HTTPS | 필수 |
| LLM 게이트웨이 | AI 챗/이미지 생성 | 해당 기능 사용 시 |
| Google Cloud Vision | AI 모더레이션 OCR | OCR 사용 시 |
| SMTP 서버 | 문의 응답 메일 | 메일 발송 시 |

> 외부 LLM 게이트웨이가 없으면 `COMMUNITY_MODERATION_ENABLED=false`, `GMS_*` 미설정 상태로 운영 가능합니다(해당 기능 비활성화).

## 12. 트러블슈팅

| 증상 | 점검 |
| --- | --- |
| OpenSearch 기동 실패 | `vm.max_map_count` 값 확인 |
| Nginx 502/503 | upstream 컨테이너 상태 및 헬스 체크 |
| Flyway 마이그레이션 실패 | `FLYWAY_ENABLED=false` 로 임시 부팅 후 SQL 확인 |
| MinIO presigned URL 접근 불가 | `MINIO_PUBLIC_URL` 이 외부에서 접근 가능한지 확인 |
| WebSocket 연결 끊김 | Nginx `/ws/` 의 timeout / proxy_set_header Upgrade 설정 |
| AI 첫 응답 지연 | 모델 워밍업 30~60초 (정상) |

## 13. Quick Start 체크리스트 (운영 배포용)

1. ☐ 호스트 OS(Linux/Windows/macOS) + Docker / Docker Compose 설치
2. ☐ `vm.max_map_count=262144` 적용 (Windows는 WSL2 설정으로)
3. ☐ 도메인 + TLS 인증서 준비
4. ☐ `.env` 작성 (시크릿 신규 발급)
5. ☐ 컴포넌트 이미지 빌드 또는 pull
6. ☐ `docker compose -f docker-compose.prod.yml up -d`
7. ☐ (선택) 모니터링 / 로깅 스택 기동
8. ☐ `/actuator/health` 200 확인
9. ☐ 관리자 계정 부트스트랩
10. ☐ 도메인 진입 → 정상 동작 확인
